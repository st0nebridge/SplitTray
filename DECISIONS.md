# Decisions

Settled architectural choices and standing constraints for this project. Read
before proposing changes to an area covered here; do not silently re-open an
active decision.

| # | Date | Decision | Status |
| - | ---- | -------- | ------ |
| 1 | 2026-09-22 | **Tray icons are captured by subclassing `Shell_TrayWnd` and reading its `WM_COPYDATA`, never by hooking `Shell_NotifyIconW`.** `Shell_NotifyIcon` runs in the *calling application's* process, so a hook on it inside `explorer.exe` only sees Explorer's own icons — proven by `tests/evidence/explorer-hook-log-2025-06-20.txt` (6 tooltips, 3 window handles, all Explorer's). | Active |
| 2 | 2026-09-22 | **The wire format is pinned by captured bytes, not by published struct definitions.** `tests/probe/shell32_wire_probe.cpp` puts its own `Shell_TrayWnd` on a private desktop and records what the real shell32 sends. The capture becomes golden buffers in `tests/regression/golden_payloads.h`. Re-run the probe and `tools/gen-golden.py` if a Windows update is suspected of changing it. | Active |
| 3 | 2026-09-22 | **One canonical wire layout, parsed defensively.** shell32 normalises every caller — ANSI, Unicode, V1–V4, 32-bit — into a single 1484-byte record with `nid.cbSize == 956`. The mod therefore has exactly one parser, bounds-checked against the received `cbData`, and logs once if the shape ever differs. No per-version layout table. | Active (refined by 57: other shapes are not read at all) |
| 4 | 2026-09-22 | **The sender's exe path comes from the wire record (offset 0x3C4), not from `OpenProcess`.** It is already there, it needs no handle and no privilege, and it works for processes the mod could not otherwise query. `GetWindowThreadProcessId` is used only for `AllowSetForegroundWindow` when forwarding a click. | Active (refined by 63: when a message carries no path, the owning window's program is asked for) |
| 5 | 2026-09-22 | **Routing is decided once per icon, at `NIM_ADD`, and is then sticky for that icon's lifetime.** Re-deciding mid-life would leave the primary tray holding an icon it can no longer be told about, or receiving a modify for an icon it never saw. Settings changes are applied by *replaying* a stored payload as `NIM_ADD` or `NIM_DELETE`, not by changing the decision on the next message. | Active |
| 6 | 2026-09-22 | **Suppression is "do not call `DefSubclassProc`", and the mod returns `TRUE`.** That is what the real tray returns, so `Shell_NotifyIcon` reports success to the caller and the application does not retry or treat the tray as absent. | Active |
| 7 | 2026-09-22 | **The full wire payload is stored per icon so decisions can be replayed or retracted.** This is what makes live settings changes, monitor hot-plug and clean unload possible without asking applications to re-register. `PayloadWithMessage` rewrites only `dwMessage`. | Active |
| 8 | 2026-09-22 | **Replays reach Explorer through a registered message posted to `Shell_TrayWnd`, handled by our own subclass, which then calls `DefSubclassProc` directly.** This runs the replay on the correct thread and cannot re-enter the mod's `WM_COPYDATA` handler. Only the mod's tray thread sends to Explorer's taskbar thread, and the subclass only ever *posts* to the tray window, so the two cannot deadlock. | Active (refined by 58: the message carries nothing; replays are queued) |
| 9 | 2026-09-22 | **Icons that pre-date the mod are collected by broadcasting `TaskbarCreated`.** It is the only supported mechanism: applications already implement it for Explorer restarts. There is no way to enumerate the existing tray contents on Windows 11, where the tray is XAML. Made optional (`repopulateOnLoad`) because a small number of applications behave oddly when asked to re-register. | Active |
| 10 | 2026-09-22 | **The secondary tray is a plain Win32 layered popup on its own thread, drawn with `DrawIconEx`.** Not XAML, not an `AppBar`. It keeps the mod independent of the Windows 11 taskbar's internals — which is what made the earlier UWP/XAML attempts fragile — and keeps all UI work off Explorer's taskbar thread. | **Superseded by 22** |
| 11 | 2026-09-22 | **`HICON`s received off the wire are copied with `CopyIcon` and owned by the mod.** USER handles are valid across processes in a session, which is how the real tray draws them, but the owning application may destroy its icon once the shell has acknowledged the message. | Active (refined by 60 and 72) |
| 12 | 2026-09-22 | **Monitor indices are 1-based over monitors sorted left-to-right, top-to-bottom, with `0` meaning "first non-primary".** `EnumDisplayMonitors` order is not documented as stable, and the displays here are arranged with the secondary at `x = -1920`; sorting gives an index that matches the physical arrangement. The monitor list is logged on load. | Active |
| 13 | 2026-09-22 | **A missing secondary monitor means every icon behaves as `primary`** — forwarded, not mirrored. An icon must never be swallowed into a tray that does not exist. (Specification requirement 7.) | Active |
| 14 | 2026-09-22 | **Only `explorer.exe` is injected.** The original specification also named `ShellHost.exe`, but `Shell_TrayWnd` is owned by Explorer, so injecting `ShellHost` would do nothing. Deliberate departure from the spec. | Active (refined by 92: only the Explorer process that shows the taskbar) |
| 15 | 2026-09-22 | **The mod stays a single `.wh.cpp` file** because Windhawk compiles one translation unit. Modularity is expressed as nine labelled sections plus the rule that sections 1–4 are pure. Testability is achieved by having `tests/harness` shadow the real Windhawk headers so the tests compile the shipped file — not by splitting the mod or duplicating logic into a test copy. | Active |
| 16 | 2026-09-22 | **The mod DLL is built directly with Windhawk's bundled clang, against a generated import library for `windhawk.dll`, with libc++ linked statically.** This makes the mod buildable and installable from the command line for CI and for scripted verification. The Windhawk UI editor remains the supported route for end users. | Active |
| 17 | 2026-09-22 | **Superseded attempts are archived under `.archive/`, not deleted.** 53 source attempts and 34 progress notes are kept for provenance; the working tree holds only what ships and what verifies it. | Active (refined by 55: kept on the development branches, not published) |
| 18 | 2026-09-22 | **Attaching to `Shell_TrayWnd` is a repeated attempt on a timer, never a one-shot at startup.** Windhawk injects into `explorer.exe` before the shell creates its taskbar, so at `Wh_ModInit` there is usually no window to attach to at all; the taskbar is also destroyed and recreated on some display, DPI and theme changes. A one-shot attach leaves the mod inert with a healthy-looking log on every real boot — which is exactly how it shipped before the first live run. | Active (refined by 92: only a taskbar this process owns) |
| 19 | 2026-09-22 | **The `TaskbarCreated` broadcast goes out only once the subclass is in place.** Asking every application to re-register into a tray the mod is not yet watching wastes the single opportunity to collect icons that pre-date the mod. | Active |
| 20 | 2026-09-22 | **The integration test runs as a child process started *on* the private desktop, not via `SetThreadDesktop`.** `SetThreadDesktop` moves only the calling thread; threads created afterwards — including the mod's own tray thread — stay on the desktop the process started on. Hooks are desktop-scoped, so the split makes `SetWindowsHookEx` fail with `ERROR_ACCESS_DENIED` and the cross-thread subclass never takes. Inside Explorer the mod's threads and the taskbar always share a desktop, so the child-process form is also the faithful one. | Active |
| 21 | 2026-09-22 | **Test doubles for Windhawk APIs must fail loudly rather than succeed vacuously.** The harness's `SetWindowSubclassFromAnyThread` originally returned `TRUE` without subclassing, which is precisely why the integration test could not catch decision 18's defect. It now mirrors Windhawk's real implementation. Any future harness stub follows the same rule. | Active |
| 22 | 2026-09-22 | **The secondary tray will be embedded in the secondary taskbar's XAML tree, not drawn as a floating window.** The 1.0.0 floating panel was rejected on sight: it must sit where the native tray sits and behave the same. A docked child window was offered as the robust alternative and the XAML route was chosen instead, with its fragility across Windows feature updates stated and accepted. Mechanism and work breakdown in `docs/xaml-injection-plan.md`. The *goal* stands; the *mechanism* is superseded by 24. | Active (mechanism superseded by 24) |
| 23 | 2026-09-22 | **The secondary taskbar has no notification area to unhide.** `Shell_SecondaryTrayWnd` contains only the XAML bridge (Start, tasks, clock, bell); unlike `Shell_TrayWnd` it has no `TrayNotifyWnd` and no tray elements at all. The tray region is therefore something this mod adds, not something it reveals. | Active |
| 24 | 2026-09-22 | **The taskbar XAML is reached by hooking `Taskbar.View.dll` symbols, not by XAML diagnostics.** `InitializeXamlDiagnosticsEx` is a single-consumer-per-process resource, and `windows-11-taskbar-styler` - which is installed and enabled here - holds it and hooks the entry point to challenge anyone else who asks for it: *"There can only be one consumer at a time. Blocking it might break that module, but allowing it might break this mod."* Every mod that actually manipulates SystemTray elements (`taskbar-tray-system-icon-tweaks`, `taskbar-clock-customization`) uses symbol hooks instead and uses no diagnostics at all. The anchor is the constructor `winrt::SystemTray::implementation::IconView::IconView`, which every tray icon passes through; the XAML element comes from the implementation object's projected interface, and the tree is walked from there with `VisualTreeHelper`. This coexists with the styler. | Active |
| 25 | 2026-09-22 | **The tray's containers are found by the names Explorer gives them, not by position.** `MainStack`, `NonActivatableStack`, `ControlCenterButton` and `NotificationCenterButton`, with icon views named `SystemTrayIcon`. Taken from `taskbar-tray-system-icon-tweaks`, which already depends on them on this Windows build. | Active |
| 26 | 2026-09-22 | **The tray anchor lives in `SystemTray.dll`, not `Taskbar.View.dll`.** Verified against the live binaries: `Taskbar.View.pdb` contains no `IconView` symbol at all, in publics or globals, while `SystemTray.pdb` has `??0IconView@implementation@SystemTray@winrt@@QEAA@XZ` along with `Stack`, `NotifyIconView`, `SystemTrayFrame`, `NotificationAreaIcons`, `NotificationAreaOverflow`, `ChevronIconView`, `SystemTrayController` and `SystemTraySecondaryController`. A mod comment naming two candidate modules is not evidence of which one is right on this build. | Active |
| 27 | 2026-09-22 | **An element is matched to its taskbar by `XamlRoot` identity, resolved from the window side.** Going element -> window is not possible without XAML diagnostics; going window -> `XamlRoot` is: `Shell_SecondaryTrayWnd` -> its `WorkerW` child -> `CSecondaryTaskBand` -> `GetTaskbarHost` -> the TaskbarHost's element -> `XamlRoot`, with the element offset recovered by disassembling `TaskbarHost::FrameHeight`. This is exact. The `XamlRoot` size and rasterization-scale comparison considered earlier is rejected: it separates the two taskbars on this machine only because the monitors differ, and ties on two identical displays. | Active (refined by 61) |
| 28 | 2026-09-22 | **Every hooked symbol is verified against the live binaries at build time** by `tools/check-symbols.py`, which resolves each module's PDB the way Windhawk does and checks the mangled names are present. Symbol hooks fail silently at runtime - the same shape as an unseeded setting - so they are measured, not assumed. | Active |
| 29 | 2026-09-22 | **Two trays, not a mirror. Placement is per icon, chosen by the user, and remembered.** `defaultTray: both` makes the secondary tray a copy of the primary one, which is not what a second tray is for. The per-process rules are a starting position; anything moved by hand overrides them and persists. The placement key is the icon's GUID where it has one, otherwise the executable file name and `uID` - never the window handle, which is a fresh value every launch and would forget the choice exactly when it matters. Stored in the mod's own storage, not its settings: it is state the mod maintains, not something to hand-edit. | Active |
| 30 | 2026-09-22 | **Plain right-click belongs to the application that owns the icon; the mod's own menu is Shift+right-click.** Taking right-click would break the thing tray icons are mostly used for. | Active |
| 31 | 2026-09-22 | **Stray control bytes are checked for at build time** by `tools/check-sources.py`. Three separate corruptions got in through shell heredocs collapsing backslash escapes: `\b` became a backspace byte in `CHANGES.md`, and `\0` became a NUL inside a character literal - where it even has the right value, so the code worked and the file was quietly corrupt. C/C++ content with escapes is written with the file tools, never through a heredoc. | Active |
| 32 | 2026-09-22 | **A cell being dragged is never removed from the panel; the cells around it move instead.** An element that leaves the visual tree loses pointer capture, which ends the drag on its first step and turns the release into a click on whatever it was dropped on - the whole reason drag-to-reorder did nothing. The step planner `SplitTray::PlanCellShift` is pure and sits outside the XAML guard so the invariant is tested rather than remembered. | Active |
| 33 | 2026-09-22 | **Dragging an icon clear of the row moves it to the other tray.** It is the gesture the second tray needs and it costs nothing extra, because the pointer is already captured. Dragging back in is not possible yet: that needs a mod-owned element on the primary taskbar, which is the remaining piece of "drag between the trays". | Active |
| 34 | 2026-09-22 | **A feature is not verified by the check count going up.** Placement shipped with 204 passing checks, none of which touched it; the harness's real storage was cited as evidence for a path nothing exercised. New behaviour names the tests that cover it, or it is reported as untested. | Active |
| 35 | 2026-09-22 | **Routing is decided from a message that carries an executable path, not from the first message seen.** Decision 5 makes routing sticky per icon, which assumed the first message about an icon is its `NIM_ADD`. It often is not: an application redrawing a live icon lands a `NIM_MODIFY` first, and a modify carries no path, so the rules have nothing to match and the icon is filed under the default tray for good. An icon whose path is unknown is *provisional*; the first message carrying one settles it, and the move goes through the settings replay rather than rewriting the decision mid-message. | Active |
| 36 | 2026-09-22 | **The embedded tray attaches by walking down from the target taskbar's `XamlRoot`, retried on the timer.** The `IconView` constructor hook only sees elements built after it is installed, and symbol resolution takes 8-15 seconds, so whether the mod ever saw an element on the secondary taskbar was a race against Explorer building it - lost on a cold boot, leaving a healthy log and no tray. The hook is kept as a trigger for taskbar rebuilds. Same defect shape as decision 18, same remedy. | Active (refined by 65: the walk anchors on a tray icon; and by 96: the symbols are resolved once, and the walk is asked for less often after ten seconds) |
| 37 | 2026-09-22 | **Both taskbars run on one UI thread, so `Shell_TrayWnd` is the way onto the secondary taskbar's XAML thread.** Verified on this machine: `Shell_TrayWnd` and `Shell_SecondaryTrayWnd` both report thread 93292. XAML objects are thread-affine, so the tray thread's timer posts a registered message to the window the mod already subclasses instead of touching XAML itself. | Active |
| 38 | 2026-09-22 | **`NIF_GUID` is not proof of a GUID; an all-zero GUID is not an identity.** The flag says the caller set it, not that it filled the field in, and applications do set it over an empty GUID - which made every such icon the same icon. Identity falls back to window and uID unless the GUID is non-empty. | Active |
| 39 | 2026-09-22 | **Re-resolving routing consults the remembered placement, never the rules alone.** `ApplySettingsToTrackedIcons` re-resolved straight from `ResolveDestination`, so any settings change silently undid every icon the user had moved by hand, against decision 29. | Active |
| 40 | 2026-09-22 | **Moving icons between the trays is done in the mod's own window, not by dragging on the taskbar.** Dragging inside Explorer's XAML island failed twice - once from a real defect (the dragged cell was removed from the panel and lost pointer capture) and once more after that was fixed, with no visible change. The arrange window is the mod's own, on its own thread, with no other claim on its input, and it moves icons in both directions, which taskbar dragging could not without a mod-owned element on the primary taskbar. Taskbar dragging is still wanted; a one-shot pointer probe stays in so the next attempt starts from evidence rather than a third guess. | Active (refined by 75: the arrange window follows the icons) |
| 41 | 2026-09-22 | **No `ImageList_DragEnter(nullptr, ...)`.** It locks the screen DC, so a drag that cannot finish wedges the whole desktop - which happened here under synthetic input. Drag feedback is a cursor change, and the drag ends itself if the mouse button is found to be up, and on `WM_CANCELMODE`, `WM_CAPTURECHANGED` and `WM_DESTROY`. | Active |
| 42 | 2026-09-22 | **Never drive the live shell with synthetic window messages that carry pointers.** `LVM_GETITEMRECT` sent across a process boundary made Explorer dereference an address in the sending process and crashed it. Cross-process checks use pointer-free messages only (`LVM_GETITEMCOUNT` and the like), or they are done in the integration test's private desktop instead. | Active |
| 43 | 2026-09-22 | **Any state the mod remembers on the user's behalf needs a way to forget it.** A placement outranks the per-process rules permanently, and there was no way back except moving every icon by hand or editing `HKLM\SOFTWARE\Windhawk\Engine\ModsWritable\local@split-tray\LocalStorage` directly. "Reset moved icons" in the tray menu, and `redeploy.ps1 -ClearPlacements` for outside the mod. | Active |
| 44 | 2026-09-22 | **A diagnostic probe is scoped to the event, not to the process.** The pointer probe was a `static bool` spent on the first drag of a session - very likely one nobody was capturing - after which every later attempt looked silent for the wrong reason. Rare events are logged every time; frequent ones are throttled to the thing that starts them. | Active |
| 45 | 2026-09-22 | **Which icons sit in the overflow is the user's choice first and the row limit's second.** It was decided by count alone, so there was no way to choose. Hidden is stored separately from placement: moving an icon between the bar and the overflow is not moving it between trays, and recording a placement for it would pin an icon the rules put there. | Active |
| 46 | 2026-09-22 | **The embedded tray is updated in place; the panel is rebuilt only when its layout changes, and never while the pointer is down.** It was cleared and rebuilt on every change to any icon, and SystemInformer changes four every second, so the cell under the pointer was destroyed several times a second - ending presses before they could become drags, closing tooltips, and leaving an open overflow popup pointing at the wrong icons. A refresh that arrives under a pressed pointer is posted to run after the release. | Active (refined by 76: a picture taken away is taken away; and by 82: only a picture that changed is drawn again) |
| 47 | 2026-09-22 | **Tooling reads names out of the mod source rather than keeping copies.** `redeploy.ps1 -ClearPlacements` kept its own list of storage value names, got one wrong (`iconOrder` for `embeddedIconOrder`), and a silent `Remove-ItemProperty` on a missing name meant the order was never cleared. It now extracts every `constexpr PCWSTR k...Value = L"..."` from the source, as `install.ps1` already does for settings, and refuses to clear if it finds none. | Active |
| 48 | 2026-09-22 | **Popups the mod shows from the taskbar are windowed (`ShouldConstrainToRootBounds(false)`).** The taskbar's XAML root is an island about 48 DIP tall, and a `Flyout` is confined to its root by default, so the overflow popup was squeezed into that strip and clipped. `MenuFlyout` defaults to its own window, which is why the mod's menu never showed it. | Active |
| 49 | 2026-09-22 | **The record replayed to put an icon back is every message folded together, drawn with the mod's own picture, and followed by the icon's version.** Refines 7. The last message is usually a partial modify, and replaying one as an add recreated the Claude usage monitor as `flags 0x2` - no callback, tooltip or path, and a picture its application had destroyed - which is how it vanished after a move and back. `FoldTrayRecord` applies each message as the shell applies a partial modify; the add carries a copy of the mod's own `HICON`; `NIM_SETVERSION` follows, because a re-added icon starts at version 0. `NIM_SETVERSION` for an icon the shell does not have is swallowed, like every other message about it (6). | Active (refined by 72: never a picture the mod does not own; and by 74: an add that is taken starts at version 0) |
| 50 | 2026-09-22 | **The mod asks applications to re-register only when Explorer will not.** Refines 9 and 19. Explorer announces each taskbar it creates once its tray is ready; the mod also asked as soon as it attached, about 14 seconds earlier, so on every Explorer start icons were registered twice, the first time into a tray that was not ready - and Desk Tray's "WhatsApp (default)", which answered only the first, was lost from the primary tray while forwarded to it. The mod asks when it was loaded into a taskbar that already existed, or when Explorer's announcement reached its window while it was not watching the tray (`ShouldAskAppsToReRegister`). | Active |
| 51 | 2026-09-22 | **Nothing slow runs on the taskbar's thread, and diagnostics that do are off unless asked for.** Every application's tray message is handled on that thread, and shell32 gives up on a tray that does not answer; an application that does not retry - Desk Tray, through Tauri's tray library - then has no icon. The XAML tree dump held the thread for 4-5 seconds during Explorer's start and cost two of Desk Tray's three icons. Frequent messages are not logged there (44), and a diagnostic setting turned on for a run is turned off again afterwards. | Active (2026-10-09: the XAML tree dump is no longer a setting but a switch in the source, from Windhawk's catalog review) |
| 52 | 2026-09-23 | **The mod answers `Shell_NotifyIconGetRect` for icons that live only in the secondary tray, with where it drew them; everything else is Explorer's to answer.** Refines 6: swallowing an icon also took away the one thing an application can ask the tray about it, and Tauri's tray library asks before it handles any click and drops the click when the answer is a failure - Telemachus's icon did nothing in the secondary tray and worked again when moved back. The question is `WM_COPYDATA` with `dwData = 3`, size then position, each packed like a mouse position (captured by the wire probe, not assumed). An icon in the overflow is reported at its chevron. | Active |
| 53 | 2026-09-23 | **Trays are numbered, and a destination names a tray.** Tray 1 is Explorer's own; Split Tray's are 2 and up - one for every display other than the primary one, left to right, then the extra trays from the settings in order (`PlanTrays`). Rules, remembered placements and the menus all use the number, and the two-tray names keep their meaning: `secondary` is tray 2, `both` is tray 2 plus the primary tray, and stored placements `p` and `s` read as trays 1 and 2. A display tray exists only while its display does, so unplugging one renumbers the display trays after it (the same arrangement-following numbering as 12); an extra tray keeps its number while its display is missing, so the extras after it do not shift. Refines 13 - the fallback is per tray - and 29. Extra trays always float, including one on the primary display: that is how the third tray was tested with two displays, chosen by the user over embedding a second tray in the primary taskbar, which would have added the first mod-owned element to the main taskbar. | Active (refined by 86: a display tray keeps its number while its display is away) |
| 54 | 2026-09-23 | **A tray cell finds its icon by a serial number, never by position.** Each icon gets a serial for its lifetime, unique even between two running copies of one application, and every cell carries it. Cells used to carry their position in the drawn order while a click looked the icon up at that position in the store - which is in registration order, not the user's order - so after a reorder, or an icon moved out and back, a click could reach a different application. | Active |
| 55 | 2026-09-23 | **The public repository is a fresh history of the curated tree, on `main`, under the MIT license.** Refines 17. Chosen by the user, as was the license. | Active (refined by 93: each release is a tagged commit on `main` with a GitHub release) |
| 56 | 2026-09-23 | **An extra tray can be disabled and keep its entry; a disabled tray keeps its number and is not there.** It is treated like an extra tray whose display is missing (53): not drawn, not offered in the menus, and its icons wait in tray 1 until it is enabled again. | 57 | 2026-09-23 | **Only the captured record shape is read; any other is left to Explorer untouched.** Refines 3. Reading a different record at the captured offsets decodes fields that are not there - an identity that is not the icon's, a folded record that replays garbage into Explorer - and staying inside the buffer does not make them right. A record whose length is not 1484 or whose `nid.cbSize` is not 956 is not intercepted at all, and the log says so once. The mod goes inert on a changed format rather than wrong. Raised by an external review. | Active |
| 58 | 2026-09-23 | **Replays are queued inside the mod and take effect when they are delivered.** Refines 8. The registered message only wakes the taskbar's thread; it carried a pointer that the subclass delivered and deleted, and any process on the desktop can post a registered message. A move records where the icon should be (`shellTarget`) when it is queued and where it is (`forwardedToShell`) when Explorer is handed it, so applications' messages in between are passed on by where the icon really is. Each move is a generation the replay carries: an add whose icon has been removed since, or moved again, is dropped - applications send and replays are posted, so an application's `NIM_DELETE` got in first and the add then recreated its icon. A removal is always delivered: taking back an icon Explorer does not have costs a failed call, not taking back one it has leaves a ghost. Raised by an external review; the race was reproduced in the integration test. | Active (refined by 66: the queue is gone; the icon store is what is settled) |
| 59 | 2026-09-23 | **The mod's window classes belong to its own module and are all unregistered before it unloads; unloading does not finish while the tray thread runs.** Windows keeps a class after the module that registered it has gone, pointing at a window procedure that is no longer there. The classes were registered against Explorer's module, and the arrange window's was never unregistered, so a reloaded mod's next arrange window would have run the unloaded one's code. The shutdown was posted only if the tray thread's window already existed, so an early unload lost it and waited out a timeout with the thread still running. It is now posted as soon as the window exists; if the thread still does not end, the module is pinned - a leak rather than a crash. Raised by an external review. | Active (refined by 67: started before attaching, stopped before the hooks go; and by 95: waited for without a time limit, never pinned) |
| 60 | 2026-09-23 | **Anything drawn after the store's lock is released draws from its own copy of the icon.** Refines 11. The store destroys the picture it replaces, on the taskbar's thread, whenever an application changes its icon; the floating trays and the arrange window, on the mod's thread, drew from bare handles copied out under the lock. `OwnedIcon` copies under the lock and destroys the copy when done. The lock is not held across drawing instead: it is the lock every application's tray message waits on (51). Raised by an external review. | Active (the embedded tray too, since the second review: its cells and overflow popup drew bare handles, and the tray thread's watchdog destroys an icon's picture when its application goes) |
| 61 | 2026-09-23 | **Embedding needs a `TaskbarHost` layout the mod recognises; an unrecognised one floats the tray.** Refines 27. Raised by an external review. | Active (2026-10-09: the ARM64 instructions are known too, from Windhawk's catalog review) |
| 62 | 2026-09-23 | **From version 3, a click is followed by what Explorer adds: `NIN_SELECT` after a left button-up, `WM_CONTEXTMENU` after a right one.** Documented for version 4, done by Explorer for 3 as well; Cairo's ManagedShell, which reimplements the tray, does the same and says so.
